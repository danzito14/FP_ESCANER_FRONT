## 0. Resumen ejecutivo (léelo primero)

- **Es viable.** Los 4 componentes del backend (Postgres+pgvector, onnxruntime, opencv-python-headless, FastAPI/uvicorn) tienen soporte ARM64/aarch64 confirmado. Nada bloquea el port.
- **El cuello de botella NO es compatibilidad, es rendimiento CPU.** Reconocer una cara ronda **sub-segundo (~0.3–0.7 s)** en la Pi 5 sin acelerador. Para un kiosko de baja concurrencia (una persona ficha a la vez) **es suficiente y aceptable como UX.**
- **NO compres el AI HAT+/Hailo.** Acelera ~6.7x, pero **rompe la paridad de embedding con buffalo_l** (obliga a recompilar a HEF, cuantizar INT8 y usar otro peso re-entrenado) → los vectores dejan de ser comparables con el roster de producción. Para este caso es un gasto que introduce un riesgo grave sin beneficio real.
- **Usa Chromium en modo kiosko, NO Electron, en la Pi.** Es lo que documenta oficialmente Raspberry Pi, propaga bien los flags de GPU de Wayland y evita la fuga de memoria GPU que Electron sufre bajo Wayland (riesgo directo dado el historial de OOM del proyecto). Reutilizas el mismo build de Angular sin reempaquetar.
- **Los 3 pilares de confiabilidad de campo:** (1) arrancar desde **NVMe** (no microSD), (2) **raíz de solo lectura (overlayfs) + partición de datos separada read-write** para la cola offline, (3) **UPS para apagado limpio + watchdog HW + systemd Restart=always**, con **Tailscale** (clave sin expiración) para gestión remota.
- **Lo que falta verificar en físico** está en la sección 9. Nada de esto se ha probado aún en una Pi real; el piloto de 1 unidad es obligatorio antes de escalar.

Todo corre en **Raspberry Pi OS 64-bit (Bookworm)** — es el único OS soportado para boot NVMe en Pi 5 (Ubuntu, Bullseye y HAOS **no** arrancan desde NVMe). Verificar `uname -m` = **aarch64** (las wheels ARM64 no instalan en 32-bit armhf).

### 2.1 Capa base
- **Raspberry Pi OS 64-bit Bookworm** (Debian 12, glibc 2.36 — cumple los mínimos de las wheels).
- **Docker Engine + Docker Compose** (paquetes ARM64 nativos de Docker; `apt` o script oficial `get.docker.com`).
- Compositor **labwc** (Wayland, default en Pi 5) para el front kiosko.

### 2.2 Contenedores (imágenes/paquetes ARM64 exactos)

**a) Base de datos — pgvector**

### 2.3 Arranque del front (Chromium kiosko bajo labwc)

Config de boot: `raspi-config → System Options → Boot/Auto Login → Desktop Autologin` (sin autologin, labwc/autostart no corre y Chromium no se lanza).

`~/.config/labwc/autostart` → llama a `kiosk.sh`:
```bash
#!/bin/sh
# 1) Verificar el nombre REAL del output (ejecuta 'wlr-randr' sin args una vez)
wlr-randr --output HDMI-A-1 --on
# 2) Evitar el diálogo "restaurar páginas" tras corte de luz
PREF=~/.config/chromium/Default/Preferences
sed -i 's/"exited_cleanly":false/"exited_cleanly":true/' "$PREF" 2>/dev/null
sed -i 's/"exit_type":"Crashed"/"exit_type":"Normal"/' "$PREF" 2>/dev/null
# 3) Lanzar Chromium kiosko
chromium http://localhost:8100 \
  --kiosk --ozone-platform=wayland \
  --noerrdialogs --disable-infobars --no-first-run --incognito \
  --use-fake-ui-for-media-stream \
  --disable-features=TranslateUI --disable-pinch \
  --overscroll-history-navigation=0 --start-maximized &
```

Detalles que ahorran días de depuración:
- **Blanking de pantalla = silenciar 3 capas:** (1) `consoleblank=0 logo.nologo=1` en `/boot/firmware/cmdline.txt`; (2) `raspi-config → Display → Screen Blanking = Off`; (3) **no** ejecutar `swayidle` con timeout (o usar `wlopm`, **nunca `xset`** en Wayland nativo).
- **Cursor:** `unclutter` NO funciona en Wayland. Usar **tema de cursor 100% transparente** (lo más robusto) o la acción `HideCursor` de labwc ≥0.8.4 disparada con `swayidle + wtype`.
- **Los autostart de LXDE/X11** (`~/.config/lxsession`, `@xset`, `unclutter`) **NO corren** bajo labwc — es la causa nº1 de "el kiosko dejó de arrancar tras actualizar a Bookworm". Todo va en `~/.config/labwc/autostart`.
- El usuario del kiosko debe estar en el grupo **`video`** para `getUserMedia`.
- Alternativa aún más minimalista sin escritorio PIXEL detrás: `cage -- chromium --kiosk http://localhost:8100`.

### 2.4 Paridad de embedding (crítico)
El vector 512-D generado en la Pi **debe coincidir** con el del pipeline de producción: mismo `w600k_r50.onnx`, mismo preprocesado (mismo tamaño de alineación 112×112, mismo orden de canales, misma normalización). Solo así la búsqueda pgvector contra el roster (creado con buffalo_l) es comparable. Correr el **mismo .onnx en onnxruntime CPU garantiza embeddings idénticos**; cualquier ruta por NPU (Hailo) los rompe.

## 3. Rendimiento esperado del reconocimiento en Pi 5

### 3.1 Cifras
- **Embedding aislado w600k_r50 (ResNet50, 12.6 GOPS) en CPU Pi 5:** ~**0.3–0.6 s/cara** en fp32 (estimación triangulada: laptop x86 ~100–200 ms × factor Pi5 4–6x). *No hay benchmark público que aísle solo el embedding en Pi 5 → medir in-situ.*
- **Pipeline completo (detección + alineación + embedding) medido en Pi 5:** **669 ms en CPU** con la config de máxima precisión (SCRFD-10g + arcface_r50); buena parte de esos ms es la detección pesada, no el embedding.
- Con detección ligera (ML Kit/MediaPipe en cliente) disparando el embedding **solo tras cara estable** (no por frame), el evento de fichaje queda holgadamente **sub-segundo**.

### 3.2 UX
Para un kiosko de **baja concurrencia** (una persona se para, mira a la cámara, confirmación por voz), **~0.5–0.7 s de latencia total es perfectamente aceptable.** No se necesita reconocimiento continuo a 15–30 FPS: basta **1 inferencia por evento de fichaje**.

### 3.3 Optimizaciones baratas en CPU (antes de pensar en NPU)
- Fijar `OMP_NUM_THREADS=4` / `intra_op_num_threads=4` en onnxruntime.
- Disparar el embedding **solo tras detección estable**, no por frame.
- Probar **cuantización INT8** del w600k_r50 (InsightFace reporta ~+0.02% de error del embedding con modelo ~4x más pequeño y ~2x más rápido) — pero **validar paridad** contra el roster antes de adoptarla en producción.
- Warmup de 5 pasadas + 20 cronometradas para tener **tu número real** en la Pi.

### 3.4 ¿Conviene el AI HAT? — **NO** para este caso
| | CPU sola (recomendado) | Hailo AI HAT+ |
|---|---|---|
| Latencia pipeline | 669 ms | 99 ms (6.7x) |
| Paridad con buffalo_l | **Idéntica** (mismo .onnx) | **Rota** (HEF + INT8 + peso re-entrenado) |
| Cambios de arquitectura | Ninguno | Reescribir detección (SCRFD, no MediaPipe) + regenerar TODO el roster |
| UX en baja concurrencia | Suficiente | Sin diferencia perceptible |

**Veredicto:** 669→99 ms **no cambia la experiencia** de un kiosko donde ficha una persona por vez, y a cambio introduce recompilación a HEF, cuantización INT8, cambio de detector y **pérdida de paridad de embedding**. El Hailo solo se justificaría si algún día se necesita **alto tráfico o video continuo**, y en ese caso habría que **regenerar todo el roster con el arcface_r50 del Hailo Model Zoo** (no mezclar embeddings de las dos fuentes). Nota: AI Kit = Hailo-8L (13 TOPS, ~mitad de rendimiento); AI HAT+ = Hailo-8 (26 TOPS); los FPS del model zoo son de Hailo-8.

## 4. Flujo offline + sync

Arquitectura offline-first correcta: **reconocer local → guardar local → subir eventos / bajar padrón al reconectar.** La clave del éxito es tratar la **sincronización como un subsistema propio**, no como "modo offline".

### 4.1 Guardado local (outbox durable = write-ahead log)
- Escribir **siempre primero** en el Postgres local (fuente de verdad del momento). La tabla de eventos de asistencia **ES el outbox**.
- Columna `estado_sync`: `PENDING → IN_FLIGHT → SYNCED`, más `RETRYABLE_ERROR`, `FATAL_ERROR`, `DEAD_LETTER` como terminales distintos. **No** colapsar todo en éxito/fallo binario.
- Columnas de control: `intentos`, `next_attempt_at`, `in_flight_since` (timestamp).
- **El outbox va en disco (partición RW persistente), nunca en memoria** — debe sobrevivir reinicios/crashes.

### 4.2 Idempotencia
- Generar un **`event_id` UUID en el DISPOSITIVO al momento de crear el evento** (no al enviarlo) y mandarlo como **idempotency-key**.
- Derivar la clave del **contenido/intento**, no del intento de transmisión (si no, cada reintento parece nuevo). Ojo con `JSON.stringify` sin ordenar claves: rompe la derivación estable.
- **En el backend central:** `UNIQUE` sobre `event_id` (o clave natural `id_trabajador + creado_en_cliente + tipo`) → un reenvío **colisiona en vez de duplicar**. Entrega **at-least-once + dedupe**, no perseguir exactly-once.

### 4.3 Reintentos y recuperación
- Errores **transitorios** (sin respuesta, 408, 429, 5xx) → reintentar con **backoff exponencial + JITTER** (el jitter evita el "thundering herd" cuando N kioskos reconectan a la vez y tumban el backend justo al volver).
- Errores **permanentes** (400/401/403/413) → `FATAL`, no reintentar (evita bucles infinitos, p. ej. payload demasiado grande).
- Tras N intentos agotados → `DEAD_LETTER` (distinto de FATAL): **preserva evidencia** para intervención humana, no pierde datos en silencio.
- **Job de recuperación de IN_FLIGHT vencidos:** si un corte de energía ocurre a mitad de envío, re-encolar los `IN_FLIGHT` cuyo `in_flight_since` supere un TTL. Sin esto → duplicados al reiniciar.
- **Lotes acotados y separados por tipo de entidad/URL** — que un error en un tipo no bloquee el resto. Nunca un único batch gigante tras días offline.

### 4.4 Bajada del padrón (delta-sync)
- El kiosko manda un **cursor/`sync_token`**; el servidor devuelve **solo los cambios** desde ese punto + un token nuevo (replay determinista). Ahorra ancho de banda, crítico en campo.
- **Tombstones para las bajas:** los borrados del padrón viajan como marca "borrado" → un trabajador dado de baja **no reaparece** en el kiosko.
- El padrón es **réplica de solo-lectura, server-wins**: el kiosko no lo edita → casi no hay conflictos reales.

### 4.5 Timestamps offline (sin NTP)
- Guardar **DOS tiempos por evento en UTC/`timestamptz`:** `creado_en_cliente` (reloj del dispositivo al escanear = hora real del evento) y `recibido_en_servidor` (al ingestar). Guardar además el **offset/zona local (ISO-8601)** y el `id_dispositivo`.
- **RTC con batería** para que el reloj del dispositivo sea razonable sin red.
- **Al reconectar:** medir y registrar el **offset reloj-dispositivo vs reloj-servidor** para poder anotar/corregir a-posteriori la deriva de los eventos creados offline (se sincroniza el dato, no el reloj).
- Para **orden/duración** (derivar 2º escaneo = salida) usar reloj **monotónico**, no wall-clock: nunca confiar en que la hora del dispositivo sea exacta al derivar entrada/salida.

### 4.6 Resolución de conflictos
- **Asistencias:** eventos **append-only inmutables** → no hay conflicto de edición, solo deduplicación por idempotencia. **Nunca Last-Write-Wins** en datos auditables.
- **Padrón:** server-wins (réplica RO); usar versión/ETag solo si algún dato se editara en ambos lados.

### 4.7 Observabilidad
- Estado de sync **visible** en el front: Encolado / Sincronizando / Sincronizado / Fallido, con "Reintentar" y "Ver pendientes". **Evitar falso éxito** (UI que dice "guardado" antes de la confirmación del servidor) y fallos silenciosos.
- Forzar sync **oportunista** apenas aparezca red y **antes de apagar** (que no se pierdan datos si el equipo se extravía).

Esto encaja directamente con la nota del proyecto `offline-sync-backend` (derivar entrada/salida por `creado_en_cliente`+TZ, reconciliar incidencias con lotes tardíos, devolver PK rechazado, completar `/candidatos`).

## 5. Hardening / confiabilidad para campo sin vigilancia

### 5.1 Almacenamiento — NVMe, NO microSD (PRIORIDAD 1)
La microSD es el **punto único de fallo en 24/7**: se corrompe en meses por escrituras sostenidas y, sobre todo, ante cortes de luz a mitad de escritura. NVMe soporta años de escritura, TRIM/SMART y sobrevive cortes repetidos.

Boot NVMe en Pi 5:
1. `/boot/firmware/config.txt`: `dtparam=pciex1` (**Gen2 certificado**; Gen3 `pciex1_gen3` es más rápido pero **NO certificado** → inestabilidad; quedarse en Gen2 para campo).
2. `sudo rpi-eeprom-config --edit`: `BOOT_ORDER=0xf416` (el `6` = intentar NVMe primero) y `PCIE_PROBE=1` en HATs no oficiales.
3. Flashear **Bookworm 64-bit** al NVMe (SD Card Copier o Imager con adaptador USB-NVMe).
4. Verificar con `lspci` / `lsblk`. **Cable FPC bien insertado** (causa frecuente de que el NVMe "desaparezca" intermitentemente — revisar antes de sellar la caja).

### 5.2 Integridad ante corte de luz (PRIORIDAD 1)
- **Raíz de solo lectura con overlayfs** (`raspi-config → Performance → Overlay File System`): dirige todas las escrituras a tmpfs en RAM; el sistema se "limpia" en cada reboot. Hay Pis 3+ años sin corrupción así.
- **⚠️ GOTCHA CRÍTICO para este proyecto:** overlayfs read-only es **incompatible con el store-and-forward** si no se aísla — la cola de fichajes iría a RAM y **se perdería al reiniciar**. **Obligatorio: partición separada montada read-write, solo para datos** (outbox/eventos Postgres, roster/CSV, cola de sync), con `data=journal`.
- **UPS para apagado limpio:** (a) **supercap** (<60s de autonomía, suficiente para `shutdown` limpio; 10.000+ ciclos, cero mantenimiento, mejor con calor) o (b) **UPS HAT 18650** (10–30 min, sigue operando en microcortes, pero la batería se degrada con calor). Para campo caluroso → **preferir supercap**. Script que dispare `shutdown -h` limpio al detectar pérdida de red eléctrica.
- `ext4` con journaling **no** basta por sí solo (si el daño toca el journal, el FS queda inconsistente) — es complemento, no sustituto de overlay + UPS.

### 5.3 Recuperación autónoma (PRIORIDAD 2)
- **Watchdog HW del SoC** en `/etc/systemd/system.conf`: `RuntimeWatchdogSec=10s` (**debe ser ≤15s** por límite del hardware Broadcom) y `ShutdownWatchdogSec=10min`. Aplicar con `systemctl daemon-reexec`, verificar con `dmesg | grep watchdog`. Atrapa **cuelgues totales del SO**.
- **systemd `Restart=always` + `RestartSec=5`** en la unidad del escáner/contenedores. Atrapa **crashes de la app**. (Docker: `restart: unless-stopped` en compose.)
- Dos capas distintas: watchdog HW = cuelgue del SO; systemd Restart = crash de app.
- Opcional: paquete `watchdog` (`/etc/watchdog.conf`) para reiniciar también por pérdida de conectividad/carga.

### 5.4 Gestión remota (PRIORIDAD 2)
- **Tailscale** (WireGuard): SSH remoto a Pis headless detrás de NAT sin abrir puertos. Provisionar con `--auth-key` reutilizable (sin login interactivo).
- **⚠️ DESHABILITAR la expiración de clave del dispositivo** en la consola admin (por defecto 180 días → si expira, se pierde el acceso remoto y no hay nadie in-situ para reautenticar).
- `tailscaled` ya es servicio systemd: reconecta solo tras reboot.
- Limitación: si la nube de coordinación de Tailscale cae, las conexiones existentes siguen pero no se abren nuevas → evaluar **Headscale self-hosted** si no se quiere depender de la nube.

### 5.5 Calor, polvo, humedad (PRIORIDAD 3)
- Caja **mínimo IP65** (Sixfab/RAKwireless o ABS DIY 200×120×75mm), UV-resistente, con **prensaestopas** para cables.
- **Membrana de venteo Gore-Tex** para igualar presión y evitar condensación/calor atrapado (una caja sellada sin venteo provoca throttling y condensación).
- **Enfriamiento pasivo** (disipador/caja de aluminio): ~±2°C sobre ambiente a plena CPU. **Evitar ventilador** (aspira polvo del campo, punto de fallo mecánico).
- Con calor, **supercap > Li-ion**.

### 5.6 Higiene operativa (PRIORIDAD 3)
- Reducir escrituras (`log2ram`/journald en RAM o `Storage=volatile`).
- Backups periódicos de la partición de datos, subidos al reconectar.
- Dejar microSD/segundo medio de rescate + RTC con batería.
- **Fuente 5V/5A obligatoria** (§1): sin ella, undervoltage + reinicios espurios que el watchdog no distingue de crashes reales.

## 6. Responsabilidades: BACKEND vs Dispositivo/Front

### 6.1 Equipo de BACKEND entrega
- **Imágenes Docker ARM64 (multi-arch o build nativo en Pi):**
  - Micro `kiosk_local` (FastAPI) con `w600k_r50.onnx` **pre-empaquetado** en la imagen (~330MB, para arranque 100% offline) y `onnxruntime>=1.21.1`.
  - `docker-compose.yml` con pgvector `pg16-bookworm` + micro, red interna, volumen de datos en la **partición RW**, `restart: unless-stopped`.
- **Contrato de sync central** (el servidor de nube que recibe eventos y sirve padrón):
  - Endpoint de ingesta idempotente (`UNIQUE` sobre `event_id`), que devuelve `recibido_en_servidor` y el **offset de reloj** para corrección a-posteriori, y el **PK rechazado** en errores.
  - Endpoint de padrón **delta-sync con cursor + tombstones**.
  - Lógica de derivar entrada/salida por `creado_en_cliente`+TZ y reconciliar incidencias con **lotes tardíos**.
- **Garantía de paridad de embedding:** confirmar mismo modelo + mismo preprocesado que producción, y publicar el vector de referencia para test de paridad (§9).
- **Build recomendado NATIVO en la Pi.** Si se construye en x86 con `docker buildx --platform linux/arm64`, es vía QEMU (lento y con riesgo de fallos sutiles) → preferir build nativo o runner ARM en CI.

### 6.2 Setup de Dispositivo / Front
- Flasheo Bookworm 64-bit + boot NVMe (eeprom, config.txt).
- Instalar Docker + levantar compose.
- Config kiosko labwc: autologin, `kiosk.sh`, flags Chromium, blanking, cursor, grupo `video`.
- Hardening: overlayfs + partición RW de datos, UPS + script de shutdown, watchdog HW, systemd Restart.
- Tailscale (auth-key + expiración deshabilitada).
- Caja IP65, cámara UVC por hub alimentado, RTC.
- **Estado de sync visible** en el front Angular + forzar sync antes de apagar.

### 6.3 Frontera clave
El front sirve la app Angular en **`http://localhost:8100`** apuntando el escáner al micro local (ya diseñado). La detección de cara (ML Kit/MediaPipe) queda en el cliente; el **embedding + búsqueda pgvector** ocurre en el micro local. **No se usa Electron en la Pi** (se reserva la cáscara Electron para el kiosko de escritorio x86 ya existente).

## 7. Fases

### Fase 0 — Preparación (backend, sin hardware de campo)
- Backend construye y publica imagen ARM64 del micro con modelo embebido.
- Definir el contrato de sync central (idempotencia, delta-sync, tombstones, doble timestamp).
- Preparar test de paridad de embedding con vector de referencia.

### Fase 1 — Piloto (1 Pi, en banco / luego 1 sitio real)
Objetivo: **validar en físico** lo que hoy es estimación.
1. Pi 5 8GB + NVMe+HAT + fuente 27W + C270 + monitor (sin caja IP65/UPS aún).
2. Flashear Bookworm, boot NVMe, levantar compose.
3. **Validar `import onnxruntime` no da Illegal instruction** en la Pi (`python -c "import onnxruntime"`).
4. **Medir latencia real** del w600k_r50 (5 warmup + 20 cronometradas).
5. **Test de paridad de embedding** contra el vector de referencia de producción.
6. Kiosko Chromium + webcam + `getUserMedia` funcionando en localhost.
7. **Prueba de estabilidad 8–24h** con cámara activa vigilando `free -m` y temperatura (era el modo de fallo del OOM en la tablet).
8. **Simular offline:** días en "airplane mode" + reconexión súbita, kill a mitad de sync, deriva de reloj, envíos duplicados. Validar dedupe, dead-letter, recuperación de IN_FLIGHT.
9. Añadir hardening completo (overlayfs + partición RW, UPS + shutdown, watchdog, Tailscale) y **repetir cortes de luz** (tirar del enchufe repetidamente).
10. Meterlo en caja IP65 en un sitio real 1–2 semanas.

**Criterios de salida del piloto:** latencia sub-segundo confirmada; paridad de embedding OK; 24h sin OOM ni throttling; 0 corrupción tras 20+ cortes de luz; sync reconcilia sin duplicados tras 3 días offline; acceso remoto Tailscale estable.

### Fase 2 — Producción (varias Pis)
- **Imagen dorada:** clonar el NVMe validado o script de aprovisionamiento reproducible (Ansible/cloud-init). No configurar cada Pi a mano.
- IDs de dispositivo únicos (`id_dispositivo` por kiosko) y auth-keys Tailscale por lote.
- Rollout escalonado (3–5 sitios) antes del despliegue completo.
- Panel central de flota (estado sync, últimas conexiones, temperatura, versión).
- **Jitter en reintentos confirmado** para que N kioskos no tumben el backend al reconectar en masa.
- Procedimiento de actualización remota vía Tailscale (imágenes Docker versionadas).

## 8. Riesgos honestos

| Riesgo | Severidad | Mitigación |
|---|---|---|
| **Paridad de embedding** Pi vs producción no exacta (preprocesado distinto) | **Alta** | Test de paridad obligatorio en Fase 1 con vector de referencia. Es el riesgo nº1 real del proyecto. |
| Latencia real > estimado (no hay benchmark del r50 aislado en Pi 5) | Media | Medir in-situ antes de comprometer SLA; INT8/XNNPACK como colchón. |
| `onnxruntime 1.21.0` → Illegal instruction (SIGILL) en aarch64 | Media (evitable) | Fijar `>=1.21.1`, validar import en la Pi. |
| overlayfs borra la cola offline si no se aísla la partición de datos | **Alta** | Partición RW separada obligatoria (§5.2). |
| Duplicados por corte de energía a mitad de sync | Media | Estado IN_FLIGHT + TTL + job de recuperación (§4.3). |
| OOM/throttling con cámara + reconocimiento (historial del proyecto) | Media | Chromium (no Electron), 8GB, prueba 8–24h, fuente 5A, enfriamiento. |
| Tailscale key expira → se pierde gestión remota | Media | Deshabilitar expiración de clave. |
| SSD con controlador Phison no bootea en Pi 5 | Baja-media | Elegir NVMe validado; probar boot antes de sellar caja. |
| Cable FPC del M.2 HAT mal insertado | Media | Verificar físicamente antes de sellar. |
| Deriva de reloj sin NTP corrompe orden entrada/salida | Media | RTC + doble timestamp + reloj monotónico + offset a-posteriori. |

**Lo que falta verificar en físico (nada de esto está probado aún en Pi real):**
1. Latencia exacta del w600k_r50 en la Pi 5.
2. Paridad bit-a-bit del embedding Pi vs backend.
3. Estabilidad 24h+ con cámara (RAM/temperatura) — validar que el OOM previo no reaparece.
4. Boot NVMe estable con el SSD concreto que se compre.
5. Integridad tras cortes de luz repetidos con overlayfs + partición RW + UPS.
6. Comportamiento de `getUserMedia` con la webcam concreta bajo Chromium/labwc en localhost.
7. Reconciliación de sync tras días offline + reconexión súbita, sin duplicados.
